# UEFI Boot Path Scaffold

This directory is no longer an `EFI_UNSUPPORTED` placeholder. It contains a real
loader/proof application in `loader.asm` plus an opt-in host artifact builder,
`build_host_artifacts.py`, that emits untracked `BOOTX64.EFI`, `esp.img`, and
`manifest.json` files for host checks. The loader can read
`VIBEOS/KERNEL.ELF` from the ESP, collect GOP framebuffer facts, capture the
UEFI memory map, and call `ExitBootServices` during the disposable-cloud OVMF
proof path. It now carries a host-buildable UEFI64-to-32-bit handoff plan in
assembly: BIOS-compatible GDT selectors, a fixed 32-bit stack target, the legacy
boot-info address layout, an internal handoff block, a low-memory trampoline
shape, and debugcon markers for the planned handoff. It still does not yet
contain a kernel-entry handoff: the current kernel still expects a BIOS-style
32-bit protected-mode entry, and the loader stops after `ExitBootServices` with
a debug marker instead of enabling the final switch from 64-bit UEFI into that
handoff. SUPPORT[UEFI] remains unclaimed in
`docs/architecture.txt`.

The remaining kernel-entry blocker is the 64-bit UEFI to 32-bit protected-mode
transition plus the proof that the ELF32 kernel was placed at its expected
low-memory PT_LOAD destinations and emitted a kernel-owned entry/status marker.

The current boot path is still the BIOS MBR plus raw-LBA Stage 2 loader described
in `docs/architecture.txt`. Future UEFI work must keep that path working unless
the project deliberately retires it, and must not describe vibe-os as
UEFI-bootable until the kernel-entry row below has real source, build, and
cloud proof evidence. `ovmf_cloud_proof.py` can emit a QEMU-free contract
manifest locally, while `.github/workflows/uefi-ovmf-proof.yml` has manual
GitHub Actions modes for an OVMF attempt or an ExitBootServices proof run.

## Machine-Readable Contract

The `UEFI_BOOT[...]` rows are machine-readable. They describe the current
intermediate rung: host-built loader pieces exist, the OVMF proof target is
ExitBootServices, and kernel entry remains blocked.

- `UEFI_BOOT[ENTRY] status=host-built requires=pe32-efi-loader proof=host-pe-coff-loader-check evidence=build-host-artifacts`
- `UEFI_BOOT[ESP_STORAGE] status=loader-implemented requires=fat-esp-kernel-read proof=source-and-host-build evidence=loader.asm`
- `UEFI_BOOT[FRAMEBUFFER] status=loader-implemented requires=gop-info-collection proof=source-and-host-build evidence=loader.asm`
- `UEFI_BOOT[MEMORY_MAP] status=loader-implemented requires=uefi-memory-map proof=source-and-host-build evidence=loader.asm`
- `UEFI_BOOT[EXIT_BOOT_SERVICES] status=cloud-proof-target requires=exit-before-kernel-handoff proof=ovmf-debugcon-marker evidence=uefi-ovmf-proof.yml`
- `UEFI_BOOT[KERNEL_HANDOFF] status=blocked requires=elf32-entry-compatible proof=future-mode-switch-handoff evidence=ovmf-proof-manifest`
- `UEFI_BOOT[BUILD_INTEGRATION] status=host-built requires=separate-opt-in-target proof=host-artifact-build evidence=build-host-artifacts`

## 32-bit Handoff Plan

This is source-level progress, not a boot claim. `loader.asm` now records a
handoff plan before `ExitBootServices` and prints a `VIBEUEFI step=handoff-plan`
debugcon marker. The marker includes the ELF32 entry address read from
`VIBEOS/KERNEL.ELF`, the protected-mode stack target, the boot-info address, the
low-memory trampoline address, the GDT base, selectors, and flags. The final
post-ExitBootServices marker remains `VIBEUEFI step=kernel-handoff
status=blocked`.

The 32-bit contract intentionally matches the current BIOS Stage 2/kernel ABI:

- code selector `0x08`, data selector `0x10`, flat 4 GiB base/limit descriptors
- stack top `0x00070000`
- legacy boot-info base `0x00007000`
- E820-compatible map target `0x00007100`
- low-memory transition trampoline target `0x00008000`
- handoff block target `0x00009000`

The planned register contract at the 32-bit trampoline is:

- `EAX`: current ELF32 kernel entry, then the jump target
- `EBX`: legacy boot-info base, `0x00007000`
- `ECX`: UEFI handoff block base, `0x00009000`
- `EDX`: handoff magic `0x444e4855` (`UHND`)
- `ESI`: E820-compatible map base, `0x00007100`
- `ESP`: protected-mode stack top, `0x00070000`
- `CS:DS/ES/FS/GS/SS`: `0x08:0x10` flat protected-mode selectors

The transition stub is deliberately not called yet. Before it can become the
real path, the loader still has to reserve or otherwise prove the fixed
low-memory ranges, copy/load ELF32 PT_LOAD segments to the kernel's expected
physical destinations instead of only reading the ELF file into an arbitrary UEFI
buffer, synthesize the legacy boot-info/E820 memory image from GOP and the UEFI
memory map, and prove a kernel-owned entry marker after the final jump.

The `UEFI_BOOT_DEVICE[...]` rows pin the future boot-device proof boundary. A
UEFI loader is not enough by itself; the proof must show how the loader is
packaged, where the kernel is read from, and which boot-device assumptions were
removed.

- `UEFI_BOOT_DEVICE[ESP_IMAGE] status=host-built requires=fat-esp-kernel-file proof=host-fat-directory-check evidence=build-host-artifacts`
- `UEFI_BOOT_DEVICE[OVMF_BOOT] status=cloud-proof-target requires=ovmf-loads-efi-from-esp proof=github-actions-ovmf evidence=uefi-ovmf-proof.yml`
- `UEFI_BOOT_DEVICE[NO_RAW_LBA_FALLBACK] status=host-checked requires=no-stage2-raw-lba-dependency proof=source-contract-check evidence=loader.asm`
- `UEFI_BOOT_DEVICE[PHYSICAL_MEDIA] status=unimplemented requires=machine-inventory-disposable-media proof=future-lab-run evidence=none`

The `UEFI_HOST_ARTIFACT[...]` rows are also machine-readable. They cover a
host-buildable x86_64 PE32+ loader/proof application, a FAT16 ESP-style image
containing `EFI/BOOT/BOOTX64.EFI` plus `VIBEOS/KERNEL.ELF`, and a source-level
guard that no OVMF/QEMU VM boot is part of the host check; the host check does
not run OVMF. These rows must not be cited as UEFI boot support. The manifest
claim is
`host-built-uefi-loader-no-kernel-entry-proof`.

- `UEFI_HOST_ARTIFACT[PE_COFF_LOADER] status=host-buildable kind=pe32plus-efi-loader-proof-application proof=host-pe-coff-loader-check evidence=build-host-artifacts`
- `UEFI_HOST_ARTIFACT[ESP_FAT_IMAGE] status=host-buildable kind=fat16-esp-file-layout proof=host-fat-directory-check evidence=build-host-artifacts`
- `UEFI_HOST_ARTIFACT[NO_VM_BOOT] status=host-checked kind=no-ovmf-or-qemu-execution proof=source-contract-check evidence=check-hardware-support-matrix`

The `UEFI_CLOUD_PROOF[...]` rows describe the opt-in cloud OVMF proof scaffold.
They are not UEFI boot evidence. Contract mode is host-only and QEMU-free, and
attempt/prove modes are restricted to GitHub Actions Ubuntu runners unless a
developer explicitly opens the Linux lab escape hatch. The default artifact
upload policy is JSON manifests only; parsed debugcon markers may appear inside
the manifest, while ESP images, EFI binaries, pflash vars, disk images, raw
serial captures, and VM logs stay runner-local scratch.

- `UEFI_CLOUD_PROOF[WORKFLOW_DISPATCH] status=scaffolded runner=github-actions-ubuntu mode=contract-attempt-prove-exitbs evidence=uefi-ovmf-proof.yml`
- `UEFI_CLOUD_PROOF[OVMF_ATTEMPT] status=scaffolded runner=github-actions-ubuntu mode=manual-qemu-ovmf-debugcon evidence=ovmf-cloud-proof-script`
- `UEFI_CLOUD_PROOF[SUPPORT_GUARD] status=guardrail runner=host-check mode=support-uefi-unclaimed evidence=check-hardware-support-matrix`
- `UEFI_CLOUD_PROOF[ARTIFACT_POLICY] status=guardrail runner=github-actions-ubuntu mode=json-manifests-only evidence=workflow-artifact-policy`

## First Implementation Rules

- Produce an explicit UEFI application artifact rather than reusing the BIOS
  Stage 1 or Stage 2 raw-sector images.
- Read the kernel from an ESP/FAT path or another documented UEFI storage path;
  do not silently depend on the current raw LBA windows.
- Prove the ESP image and OVMF boot path before any physical-media experiment;
  physical hardware notes must include exact machine inventory and disposable
  media details.
- Fill a boot-info handoff that preserves the existing kernel expectations for
  memory, framebuffer, protected-mode entry, and entry point data, or change
  those expectations with a matching host-checked contract.
- Keep `ExitBootServices` before kernel entry and document which firmware
  services, if any, are intentionally unavailable afterward.
- Add a host-only build/check target before any local VM proof, and keep local
  VM execution behind the existing opt-in safety rail.
- Keep OVMF proof runs opt-in on disposable cloud runners until the loader emits
  a kernel-entry proof marker; contract checks must not require local Mac QEMU.
- Keep WADs, disk images, screenshots, pixel dumps, raw audio, and VM logs out of
  git and out of default proof artifacts.
