# UEFI Boot Path Scaffold

This directory is no longer an `EFI_UNSUPPORTED` placeholder. It contains a real
loader/proof application in `loader.asm`. The loader can read
`VIBEOS/KERNEL.ELF` from the ESP, collect GOP framebuffer facts, capture the
UEFI memory map, call `ExitBootServices`, and attempt the handoff to the current
32-bit protected-mode kernel during the disposable-cloud OVMF proof path. It now
carries host-buildable UEFI64-to-32-bit handoff assembly: fixed low-memory
reservations, ELF32 `PT_LOAD` placement at physical destinations under the same
low-memory bounds as BIOS Stage 2, a synthesized and validated legacy
boot-info/E820 block, BIOS-compatible GDT selectors, a fixed 32-bit stack
target, an internal handoff block, a low-memory 64-bit mode-exit stub, a
low-memory 32-bit trampoline, a pre-`ExitBootServices` verification pass over
the copied low-memory handoff image, and debugcon markers for the attempted
handoff.
The kernel now has a source-level `VIBEKERN step=uefi-entry` marker and smoke
status fields for the UEFI handoff registers/block. This still does not claim
UEFI boot support for this checkpoint until a disposable OVMF run captures the
kernel-owned marker after `ExitBootServices`.

The kernel-entry proof is green for this checkpoint: prove-mode cloud run
`26289526249` built the PE/COFF loader and a dual BIOS/UEFI FAT16 disk image
that also carries the BIOS boot files, Doom ELF, and WAD, booted disposable
OVMF, and captured the kernel-owned `VIBEKERN step=uefi-entry status=OK` marker.
The remaining blocker is proving that the UEFI path continues through the
kernel's ATA/FAT file path into Doom gameplay. The playable game path still uses
the BIOS/IDE disk layout.

The current boot path is still the BIOS MBR plus raw-LBA Stage 2 loader described
in `docs/architecture.txt`. Future UEFI work must keep that path working unless
the project deliberately retires it, and must not describe vibe-os as
UEFI-bootable until the kernel-entry row below has real source, build, and
cloud proof evidence. `.github/workflows/uefi-ovmf-proof.yml` currently checks
the loader assembly contract, builds a real `BOOTX64.EFI`, packages a GPT/FAT
ESP image, and can run disposable OVMF in attempt/prove modes without the
retired scripting stack.

## Machine-Readable Contract

The `UEFI_BOOT[...]` rows are machine-readable. They describe the current
intermediate rung: host-built loader pieces exist, the OVMF proof target is the
kernel-owned entry marker, and the loader has a bounded low-memory handoff
layout check.

- `UEFI_BOOT[ENTRY] status=host-built requires=pe32-efi-loader proof=host-pe-coff-loader-check evidence=build-host-artifacts`
- `UEFI_BOOT[ESP_STORAGE] status=loader-implemented requires=fat-esp-kernel-read proof=source-and-host-build evidence=loader.asm`
- `UEFI_BOOT[FRAMEBUFFER] status=loader-implemented requires=gop-info-collection proof=source-and-host-build evidence=loader.asm`
- `UEFI_BOOT[MEMORY_MAP] status=loader-implemented requires=uefi-memory-map proof=source-and-host-build evidence=loader.asm`

## 32-bit Handoff Implementation

This is source-level progress, not a boot claim. `loader.asm` now reserves the
fixed low-memory pages, validates the ELF32 header/program headers with
BIOS-compatible bounds, loads ELF32 `PT_LOAD` segments to their physical
destinations, synthesizes and validates the legacy boot-info/E820 block from GOP
plus a UEFI memory map whose descriptor size and byte span are checked before it
can feed E820 synthesis, copies a low-memory 64-bit transition stub and 32-bit
trampoline, verifies that the low handoff block, trampoline, and transition stub
are readable at their physical targets, then prints
`VIBEUEFI step=kernel-handoff status=attempting` after `ExitBootServices` before
jumping to the low transition stub. If the kernel is entered through that path,
`kernel/kernel.asm` validates `EDX=UHND`,
`EBX=0x7000`, `ECX=0x9000`, and `ESI=0x7100`, copies the handoff block into
kernel-owned status fields, emits `VIBEKERN step=uefi-entry status=OK` on the
same OVMF debugcon port, and appends `uefi=`, `uefiregs=`, `uefientry=`,
`uefifb=`, `uefimmap=`, and `uefiboot=` smoke fields. The
`VIBEUEFI step=handoff-plan` marker includes the ELF32 entry address read from
`VIBEOS/KERNEL.ELF`, the protected-mode stack target, the boot-info address, the
low-memory trampoline address, the low GDT base, selectors, loaded segment
count, transition stub address, and flags.

The 32-bit contract intentionally matches the current BIOS Stage 2/kernel ABI:

- code selector `0x08`, data selector `0x10`, flat 4 GiB base/limit descriptors
- stack top `0x00070000`
- legacy boot-info base `0x00007000`
- E820-compatible map target `0x00007100`
- low-memory transition trampoline target `0x00008000`
- handoff block target `0x00009000`
- low-memory 64-bit transition stub target `0x0000a000`

The planned register contract at the 32-bit trampoline is:

- `EAX`: current ELF32 kernel entry, then the jump target
- `EBX`: legacy boot-info base, `0x00007000`
- `ECX`: UEFI handoff block base, `0x00009000`
- `EDX`: handoff magic `0x444e4855` (`UHND`)
- `ESI`: E820-compatible map base, `0x00007100`
- `ESP`: protected-mode stack top, `0x00070000`
- `CS:DS/ES/FS/GS/SS`: `0x08:0x10` flat protected-mode selectors

The transition stub is now called after `ExitBootServices`, and a disposable
OVMF run has captured the existing loader markers and then the kernel-owned
`VIBEKERN` entry/status marker after the final jump. The `prove` checker treats
`ExitBootServices` as loader-only evidence and requires the loader's
post-`ExitBootServices` `kernel-handoff status=attempting` marker plus the
kernel-owned entry marker. The post-`ExitBootServices` `kernel-handoff` marker
is not accepted as proof unless it carries the bounded target addresses and
masks that the trampoline will use: `entry32`, `handoff=0x00009000`,
`bootinfo=0x00007000`, `e820=0x00007100`, `tramp32=0x00008000`,
`transition64=0x0000a000`, `flags`, and `segments`. A bare loader message that
only says it attempted the handoff is treated as an overclaim.

The `UEFI_BOOT_DEVICE[...]` rows pin the future boot-device proof boundary. A
UEFI loader is not enough by itself; the proof must show how the loader is
packaged, where the kernel is read from, and which boot-device assumptions were
removed.

- `UEFI_BOOT_DEVICE[DUAL_FAT16_IMAGE] status=cloud-proven requires=efi-boot-file-plus-bios-and-doom-files proof=github-actions-ovmf evidence=uefi-ovmf-proof.yml`
- `UEFI_BOOT_DEVICE[OVMF_BOOT] status=cloud-proven requires=ovmf-loads-efi-from-esp proof=github-actions-ovmf evidence=uefi-ovmf-proof.yml`
- `UEFI_BOOT_DEVICE[NO_RAW_LBA_FALLBACK] status=host-checked requires=no-stage2-raw-lba-dependency proof=source-contract-check evidence=loader.asm`
- `UEFI_BOOT_DEVICE[PHYSICAL_MEDIA] status=unimplemented requires=machine-inventory-disposable-media proof=future-lab-run evidence=none`

The `UEFI_HOST_ARTIFACT[...]` rows are also machine-readable. They cover a
host-buildable x86_64 PE32+ loader/proof application, a FAT16 ESP-style image
containing `EFI/BOOT/BOOTX64.EFI` plus `VIBEOS/KERNEL.ELF`, and a source-level
guard that no OVMF/QEMU VM boot is part of the host check; the host check does
not run OVMF. These rows must not be cited as UEFI boot support. The manifest
claim is
`host-built-uefi-loader-no-kernel-entry-proof`; its `kernel_handoff` field is
`source-implemented-pending-ovmf-kernel-entry-marker`. The host artifact builder
validates the generated `BOOTX64.EFI` PE/COFF boundary before writing the
manifest: `MZ` plus `PE\0\0` signatures, x86_64 PE32+ optional header, EFI
application subsystem, one executable/readable/writable `.text` section at the
expected entry RVA, and the required loader debug markers.

- `UEFI_HOST_ARTIFACT[PE_COFF_LOADER] status=host-buildable kind=pe32plus-efi-loader-proof-application proof=host-pe-coff-loader-check evidence=build-host-artifacts`
- `UEFI_HOST_ARTIFACT[ESP_FAT_IMAGE] status=host-buildable kind=fat16-esp-file-layout proof=host-fat-directory-check evidence=build-host-artifacts`
- `UEFI_HOST_ARTIFACT[NO_VM_BOOT] status=host-checked kind=no-ovmf-or-qemu-execution proof=source-contract-check evidence=check-hardware-support-matrix`

The `UEFI_CLOUD_PROOF[...]` rows describe the opt-in cloud OVMF proof scaffold.
Contract mode is host-only and QEMU-free; attempt/prove modes are restricted to
GitHub Actions Ubuntu runners unless a developer explicitly opens the Linux lab
escape hatch. Attempt mode must see loader markers through the post-ExitBootServices
handoff attempt. Prove mode must also see the kernel-owned
`VIBEKERN step=uefi-entry status=OK` marker. The workflow also captures
kernel-owned guest status booleans for ATA, partition, WAD, and Doom progress;
those fields are diagnostic until they all report green in the JSON manifest.
The default artifact upload policy is JSON manifests only; ESP images, EFI
binaries, pflash vars, disk images, raw serial captures, and VM logs stay
runner-local scratch.

- `UEFI_CLOUD_PROOF[WORKFLOW_DISPATCH] status=scaffolded runner=github-actions-ubuntu mode=contract-attempt-prove-kernel-entry evidence=uefi-ovmf-proof.yml`
- `UEFI_CLOUD_PROOF[OVMF_ATTEMPT] status=cloud-proven runner=github-actions-ubuntu mode=qemu-ovmf-debugcon evidence=uefi-ovmf-proof.yml`
- `UEFI_CLOUD_PROOF[KERNEL_ENTRY_PROOF] status=cloud-proven runner=github-actions-ubuntu mode=ovmf-kernel-entry-marker evidence=uefi-ovmf-proof.yml`
- `UEFI_CLOUD_PROOF[GUEST_STORAGE_DIAGNOSTIC] status=diagnostic runner=github-actions-ubuntu mode=status-page-json evidence=uefi-guest-status.json`
- `UEFI_CLOUD_PROOF[SUPPORT_GUARD] status=guardrail runner=host-check mode=support-uefi-unclaimed evidence=check-hardware-support-matrix`
- `UEFI_CLOUD_PROOF[ARTIFACT_POLICY] status=guardrail runner=github-actions-ubuntu mode=json-manifests-only evidence=workflow-artifact-policy`

## First Implementation Rules

- Produce an explicit UEFI application artifact rather than reusing the BIOS
  Stage 1 or Stage 2 raw-sector images.
- Read the kernel from an ESP/FAT path or another documented UEFI storage path;
  do not silently depend on the current raw LBA windows.
- Prove the ESP image and OVMF boot path before any physical-media experiment;
  physical hardware notes must include exact machine inventory and disposable
  media details.
- Fill a boot-info handoff that preserves the existing kernel expectations for
  memory, framebuffer, protected-mode entry, and entry point data, or change
  those expectations with a matching host-checked contract.
- Keep `ExitBootServices` before kernel entry and document which firmware
  services, if any, are intentionally unavailable afterward.
- Add a host-only build/check target before any local VM proof, and keep local
  VM execution behind the existing opt-in safety rail.
- Keep OVMF proof runs opt-in on disposable cloud runners until the loader emits
  a kernel-entry proof marker; contract checks must not require local Mac QEMU.
- Keep WADs, disk images, screenshots, pixel dumps, raw audio, and VM logs out of
  git and out of default proof artifacts.
