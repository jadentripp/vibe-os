# Proof And Gaps

This file is intentionally short. The project no longer treats a large host
script suite as the source of truth. New claims should come from guest OS status
fields, assembly/C code running in vibe-os, tiny C host validators, shell
workflow checks, and disposable cloud boots.

## Current Playable Claim

vibe-os can boot in cloud QEMU and play the original `linuxdoom-1.10` port with
real shareware `DOOM1.WAD` through Codespaces/noVNC.

The meaningful current claims are:

- BIOS boot path reaches the 32-bit kernel and Stage 2 prefers the FAT16
  `KERNEL.ELF` file before the raw-LBA fallback after validating the file's
  FAT16 cluster bounds and end-of-chain marker.
- The kernel owns interrupts, paging, timer ticks, input, framebuffer, storage,
  a heap, syscalls, and user process launch.
- Doom runs as a Ring 3 ELF process, not as a host app.
- Doom reads WAD data through the OS file path and presents frames through the
  OS graphics path.
- The safe manual play path runs QEMU only on a disposable cloud host.

## Proof Commands

Host-only checks:

```sh
make ALLOW_LOCAL_VM=0 DOOM_WAD= build-only
make ALLOW_LOCAL_VM=0 DOOM_WAD= test
make ALLOW_LOCAL_VM=0 DOOM_WAD= playability-host-check
```

`tools/vibe_status_check.c` is the current compiled host validator for guest
status text. It is intentionally small and should not grow into a replacement
operating system.

Disposable cloud checks:

```sh
gh workflow run os-smoke.yml --ref main -f expected_ref=main
gh workflow run real-wad-smoke.yml --ref main -f expected_ref=main
```

Manual play:

```sh
./tools/play_now_codespaces.sh --repo jadentripp/vibe-os --ref main
```

## Gap Ledger

- `GAP[UEFI_BOOT] status=partial`: prove-mode cloud run `26288958164` on
  `main` built `BOOTX64.EFI`, booted disposable OVMF, passed
  `ExitBootServices`, attempted the 64-bit-to-32-bit handoff, and captured the
  kernel-owned `VIBEKERN step=uefi-entry status=OK` marker. The workflow now
  packages the UEFI loader into the same FAT16 disk-image layout that also
  carries `DOOM.ELF` and `DOOM1.WAD`; the next proof needs to show that exact
  dual image still reaches the kernel marker. The remaining gap after that is
  proving that the UEFI boot path continues through the kernel's ATA/FAT file
  path into Doom gameplay.
- `GAP[HIGHER_HALF_EXEC] status=open`: the kernel has high mapping proof work,
  but "done" means the live kernel actually executes from its higher-half
  virtual address.
- `GAP[PREEMPTION] status=open`: scheduler accounting is not enough; done means
  timer IRQ preemption switches Ring 3 contexts through saved frames and `iret`.
- `GAP[STORAGE_GENERALITY] status=open`: FAT/WAD/save paths must keep becoming
  a general block-device and VFS subsystem for other programs.
- `GAP[INPUT_GENERALITY] status=open`: keyboard and mouse should feed one
  generic event queue consumed by any process.
- `GAP[GRAPHICS_GENERALITY] status=open`: framebuffer presentation should be a
  normal OS device ABI, not a Doom-only path.
- `GAP[AUDIO_GENERALITY] status=open`: SB16/DMA/PCM should become a generic
  audio device that a second program can write to.
- `GAP[HOST_SCRIPT_RETIREMENT] status=in-progress`: legacy host scripts have
  been removed from the repo; remaining proof must stay shell/C/guest-owned.
- `GAP[PHYSICAL_HARDWARE] status=open`: QEMU PC hardware is the supported target.
  ACPI, HPET probing, and LAPIC/IOAPIC routing are only claimed inside that
  supported cloud QEMU machine model. Arbitrary laptops, disks, USB, AHCI, HDA,
  and real install recovery are not claimed.

## Evidence Standard

Do not claim a subsystem is done because a host tool inferred it. Claim it when
the OS emits status from the guest, a cloud boot exercises it, and the relevant
assembly/C path is visible in the repo.

WADs, generated disks, screenshots, raw audio, framebuffer dumps, and VM logs
must stay out of git and off the Mac.
