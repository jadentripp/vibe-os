# Architecture

vibe-os is a small x86 operating system built around a concrete target: boot
into the original Doom engine and make the OS services real enough that other
small games can use them later.

## Target

- Architecture: 32-bit x86 protected mode.
- First supported machine: QEMU PC with BIOS, IDE/ATA, PS/2, VBE-style
  framebuffer, PIT plus LAPIC/IOAPIC IRQ routing with PIC fallback, and
  SB16-compatible audio.
- Play path: cloud QEMU through Codespaces/noVNC.
- Local Mac: build-only unless the user explicitly opts into local VM risk.

## Boot

`boot/stage1.asm` is the MBR. It loads `boot/stage2.asm` from disk using BIOS
disk services. Stage 2 collects boot facts, enables A20, builds the GDT, enters
protected mode, loads the kernel ELF, and jumps to it.

`boot/uefi/loader.asm` is an assembly UEFI path. It is real source work, but not
the supported play path yet. The remaining UEFI work is PE/COFF packaging,
GOP/memory-map handoff, `ExitBootServices`, and a proven handoff into the same
kernel.

## Kernel

The main kernel body is `kernel/kernel.asm`. It owns:

- GDT, IDT, exception stubs, IRQ stubs, and syscall entry.
- Paging, early physical memory accounting, guard pages, and higher-half proof
  work.
- PIT clock ticks, APIC/IOAPIC IRQ routing on the supported QEMU target, and
  PIC fallback.
- HPET-backed monotonic milliseconds after ACPI/HPET probing succeeds, while
  preserving the 100 Hz compatibility tick ABI expected by user programs.
- Ring 3 process entry and user/kernel transitions.
- ATA/IDE PIO, MBR/FAT image layout, file descriptors, reads, writes, seeks,
  config files, save files, and WAD loading.
- PS/2 keyboard and mouse state.
- Framebuffer device state and present path.
- SB16-style PCM/audio status and DMA-oriented plumbing.
- Panic, serial/debug output, and machine-state status fields.

Some support code is C because Doom is C and because tiny host tools are clearer
there. OS legitimacy should still move toward assembly at CPU, driver, and ABI
boundaries.

## Userland

`user/crt0.asm` enters Ring 3. `user/runtime.c` is the small C runtime and
syscall wrapper surface for probe programs. Doom is linked as `DOOM.ELF` from
the original id Software source plus the local `doom_port/` platform layer.

The original vendor source under `third_party/doom` must remain pristine.

## Storage

The disk image has a simple raw boot area followed by a FAT16 partition. Doom,
probe programs, configs, saves, and assets are ordinary files in that image.

This is not yet an installable general-purpose disk OS. The current goal is a
general block/FAT/file-descriptor subsystem inside the supported QEMU disk
model, not arbitrary-media recovery.

## Graphics And Input

Doom renders a 320x200 indexed framebuffer. vibe-os owns the palette conversion
and present path. The long-term design is a generic framebuffer ABI so other
programs can draw without knowing about Doom.

Keyboard and mouse input should flow into a generic event queue. Doom is one
consumer, not the definition of the input system.

## Audio

Audio is meant to become a generic PCM device. Doom sound effects and music
should sit above that device, while SB16/DMA/ring-buffer mechanics stay in the
kernel.

## Proof Philosophy

The old host-script proof stack has been removed. The acceptable proof stack is now:

- assembly/C code in the guest,
- guest-emitted status fields,
- small C host utilities for image/link/status checks such as
  `tools/vibe_status_check.c`,
- shell in Make and GitHub Actions,
- disposable cloud QEMU runs.

If a claim cannot be checked without rebuilding a large host tool suite, leave
the claim open and move the evidence into the OS.
